# HOUSEHUB

Expense splitting, settlements and chores for shared houses — with XP, levels, achievements and a
leaderboard, so tidying up the kitchen is at least mildly competitive.

Built as a MERN application: React + Vite on the front, Express + MongoDB on the back, and one small
`shared/` module both halves import for the money and XP mathematics. The UI is its own design system
on top of Tailwind, with Radix primitives for dialogs, menus and tooltips, Framer Motion for
transitions, and Sonner for toasts.

Three decisions shape the whole codebase:

- **No drift between client and server.** The split a user previews in the expense form is literally
  the function the server runs, because both import `shared/money.js`.
- **Balances are derived, never stored.** Delete an expense and every balance is instantly correct.
- **The URL is never the authorisation.** Every house-scoped route proves membership before a
  controller runs, so swapping a house id returns `403`, not another house's data.

## Features

- **Accounts** — register, sign in, JWT sessions, profile editing, change password, forgot/reset
  password, delete account.
- **Houses** — create, join by invite link or code, members with roles, role changes, ownership
  transfer, member removal, leave (the house cleans itself up when the last member goes).
- **Expenses** — search, filter, sort and paginate. Split equally, by exact amounts, or by
  percentage, with a receipt URL and description.
- **Balances** — derived on read. Shows both your pairwise position ("you owe X, Y owes you") and the
  minimal set of payments that settles the whole house.
- **Settlements** — record a payment; it moves the ledger only once the receiver confirms it.
  Confirm, reject, remind, cancel.
- **Chores** — assignee, due date, priority and XP reward. Start, complete, edit, delete. Overdue is
  derived, never stored. "My Chores" buckets work into overdue / today / upcoming / completed.
- **Gamification** — XP credited exactly once per chore, a non-linear level curve, achievements that
  unlock from server-side counters, a dense-ranked leaderboard, and an activity feed.
- **Dashboard & analytics** — spend, what you owe, what you're owed, chores, top of the leaderboard
  and recent activity in one request; spend by month, category and member.
- **Notifications** — generated by house activity, with an unread count in the header.
- **Interface** — a Tailwind design system with semantic tokens, glass/gradient surfaces, real motion,
  and dark-first light/dark/system theming applied before first paint.

## Quick start

**Prerequisites:** Node.js **18.17+** and MongoDB running locally (or an Atlas connection string).

```bash
# 1. Install everything (root, server and client, via the postinstall hook)
npm install

# 2. Configure the API
cp server/.env.example server/.env
#    then set a real JWT_SECRET. Generate one with:
#    node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

# 3. Start MongoDB if it is not already running
mongod --dbpath /path/to/data

# 4. Optional: load the demo house
npm run seed

# 5. Run the API and the web app together
npm run dev
```

The API runs on `http://localhost:5000` and the web app on `http://localhost:5173`. Register from the
app, or sign in as a demo user below.

The client needs no `.env` locally: `client/vite.config.js` proxies `/api` to `localhost:5000`, so
there is no absolute URL to keep in sync and no CORS preflight during development.

## How it works

### Layers

`routes/` wires URLs to middleware and controllers. `middleware/` handles auth, membership, validation
and rate limits. `controllers/` read the request and call a service — no business rules. `services/`
hold the logic. `models/` hold the schemas and indexes. `utils/` holds the response envelope,
pagination, serializers and logger.

### Request lifecycle

```
Browser (axios, Authorization: Bearer <jwt>)
  → Vite dev proxy (/api → :5000)            [dev only]
  → Express: helmet → cors → json → morgan → apiLimiter
  → protect        verify JWT, load user
  → houseScope     load house, prove membership
  → role guard     manager / owner where required
  → validators    400 / 422 with field details
  → controller → service → MongoDB
  → { success, data, meta?, message? }
```

### One error shape

Every failure is `{ "success": false, "message": "..." }`, optionally with `details` for field-level
messages. The client normalises network failures and unexpected HTML into the same shape, so
`error.message` is always safe to show and no stack trace reaches the screen.

### Money is integer paise, everywhere

`₹2,400` is stored as `240000`. Floating-point rupees never exist — not in the database, not in the
API, not in a request body. Rupees appear only as formatted strings (`formatPaise`).

### Splits add up, and the remainder is deterministic

`₹100` split three ways is `3334 / 3333 / 3333` paise. The remainder is handed out one paise at a time
with participants sorted by user id, so the same expense always yields the same shares regardless of
the order the client sent. Percentage splits use the largest-remainder method.

The server never trusts client-computed shares: equal and percentage splits are recomputed, and a
custom split must sum to the total. A mismatch is a `400`, not a ledger quietly off by a paisa.

### Balances are derived, never stored

There is no `currentBalance` field anywhere. Every read rebuilds the ledger from all expenses plus
confirmed settlements, giving two views of the same data:

- the **pairwise ledger** answers "who owes whom" (what the dashboard shows);
- **minimise transfers** answers "what is the fewest payments that zeroes the house out".

Only confirmed settlements move the ledger — pending and rejected ones do not.

### XP is credited exactly once

`POST /api/houses/:houseId/chores/:choreId/complete` takes no request body. XP comes from the stored
chore (validated against an allow-list at creation), so a client cannot submit its own. Completion is
two idempotent conditional writes, because a standalone MongoDB has no transactions:

1. flip `status` to `completed` only if it isn't already;
2. flip `xpAwarded` to `true` only if it isn't already — the XP claim token.

If the process dies between the two, the chore is completed but unclaimed, so XP is credited on the
next attempt and never twice. Five concurrent completions is a test case. XP goes to the **assignee**,
even if a manager pressed the button.

## Roles and permissions

A member's role lives on `House.members[].role`. `houseScope` always proves membership; role guards
gate privileged actions.

| Action                                            | Member | Admin | Owner |
| ------------------------------------------------- | :----: | :---: | :---: |
| View dashboard, balances, analytics, activity     |   ✅   |  ✅   |  ✅   |
| Create / edit / delete your own expense           |   ✅   |  ✅   |  ✅   |
| Edit / delete another member's expense            |   —    |  ✅   |  ✅   |
| Create a chore; start / complete your own chore   |   ✅   |  ✅   |  ✅   |
| Start / complete someone else's chore             |   —    |  ✅   |  ✅   |
| Request a settlement; confirm one sent to you     |   ✅   |  ✅   |  ✅   |
| Edit house settings, regenerate the invite code   |   —    |  ✅   |  ✅   |
| Remove another member                             |   —    |  ✅   |  ✅   |
| Change a member's role                            |   —    |   —   |  ✅   |
| Transfer ownership                                |   —    |   —   |  ✅   |
| Leave the house                                   |   ✅   |  ✅   |  ✅\* |

\* An owner with other members must transfer ownership before leaving; the last member out deletes the
house. Every rule here is exercised in `server/tests/security.test.js`.

## Environment variables

Each package owns its own file; both `.env` files are git-ignored and the committed `.env.example`
files document every variable.

| File          | Required | Notes                                                                        |
| ------------- | -------- | ---------------------------------------------------------------------------- |
| `server/.env` | Yes      | Database, JWT secret, CORS origins. Copy from `server/.env.example`.          |
| `client/.env` | No       | Only needed to point the SPA at a remote API. Unset in development by design. |

### `server/.env`

| Variable               | Default                              | Purpose                                                       |
| ---------------------- | ------------------------------------ | ------------------------------------------------------------- |
| `NODE_ENV`             | `development`                        | `production` enables strict config checks.                    |
| `PORT`                 | `5000`                               | API port.                                                     |
| `MONGO_URI`            | `mongodb://127.0.0.1:27017/househub` | Database connection string.                                   |
| `JWT_SECRET`           | insecure dev fallback                | **Required in production, minimum 32 characters.**            |
| `JWT_EXPIRES_IN`       | `7d`                                 | Session lifetime.                                             |
| `CLIENT_URL`           | `http://localhost:5173`              | Comma-separated CORS allow-list.                              |
| `BCRYPT_ROUNDS`        | `12`                                 | Drop to `4` in tests for speed.                               |
| `RATE_LIMIT_WINDOW_MS` | `900000`                             | Broad API rate-limit window.                                  |
| `RATE_LIMIT_MAX`       | `600`                                | Requests per window, per IP.                                  |
| `AUTH_RATE_LIMIT_MAX`  | `30`                                 | Tighter budget for credential endpoints.                      |
| `EMAIL_DEV_MODE`       | `true` (non-production)              | Log reset links to the console instead of emailing.           |
| `CLOUDINARY_*`         | empty                                | Uploads stay disabled until all three are set.                |
| `WEEKLY_CHORE_GOAL`    | `50`                                 | Default weekly house chore goal.                              |

### `client/.env`

| Variable       | Notes                                                                                     |
| -------------- | ----------------------------------------------------------------------------------------- |
| `VITE_API_URL` | Leave **unset** in development. In production set it to the deployed API root **including `/api`**, e.g. `https://househub-api.onrender.com/api`. |

With `NODE_ENV=production`, the server refuses to start without a real `MONGO_URI`, a `JWT_SECRET` of
at least 32 characters, and a `CLIENT_URL`.

## API reference

All routes are prefixed with `/api`. Everything except register, login and password reset requires
`Authorization: Bearer <token>`.

**Envelopes**

```jsonc
// Success
{ "success": true, "data": {}, "message": "Optional", "meta": {} }
// Failure
{ "success": false, "message": "...", "details": [ { "field": "email", "message": "..." } ] }
```

Paginated endpoints accept `?page=` and `?limit=` (max 100) and return
`meta: { page, limit, total, pages, hasNextPage, hasPrevPage }`. Sorting is `?sort=field:asc|desc`,
restricted to a per-endpoint allow-list.

| Code | Meaning                                                    |
| ---- | ---------------------------------------------------------- |
| 200  | OK                                                         |
| 201  | Created                                                    |
| 400  | Bad input (bad JSON, bad cast, invalid field)              |
| 401  | Missing, malformed or expired token                        |
| 403  | Not a member, or insufficient role                         |
| 404  | Not found                                                  |
| 409  | Conflict (duplicate email / invite code)                   |
| 422  | Validation failed — includes field-level `details`         |
| 429  | Rate limited                                               |
| 500  | Unexpected — logged server-side, generic message returned  |

### Example — add an expense (₹4,000 groceries split four ways)

`amount` is **integer paise**. Equal-split shares are recomputed server-side, so the client only sends
the participants.

```http
POST /api/houses/:houseId/expenses
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "title": "Monthly groceries",
  "amount": 400000,
  "category": "groceries",
  "paidBy": "<atulId>",
  "splitType": "equal",
  "participants": [ { "user": "<atulId>" }, { "user": "<rahulId>" },
                    { "user": "<amanId>" },  { "user": "<riyaId>" } ]
}
```

The server stores `share: 100000` per participant. A custom split instead sends `share` (paise) per
participant and must total the amount; a percentage split sends `percentage` per participant and must
total 100.

## Deployment

Three services, none of which need a container.

**Database — MongoDB Atlas.** Create a free cluster and database user, allow access from `0.0.0.0/0`
(Render's free-tier outbound IPs are not fixed), and copy the connection string into `MONGO_URI`.

**API — Render.**

- Build command: `cd server && npm install`
- Start command: `cd server && npm start`

Set `NODE_ENV=production`, `MONGO_URI`, a real random `JWT_SECRET`, `JWT_EXPIRES_IN`, and `CLIENT_URL`
(your Vercel URL). `PORT` is provided by Render — do not set it. `GET /api/health` is an
unauthenticated liveness probe.

**Web app — Vercel.**

- Root directory: `client`
- Build command: `npm run build`
- Output directory: `dist`

Set `VITE_API_URL` to the Render URL including `/api`. Note that `client/vite.config.js` aliases
`@shared` to `../shared`, which sits outside the client directory — Vercel builds from the repository
root so this resolves correctly, but a narrower root directory setting will fail on that import.

## Not in this release

Deliberately deferred, so nobody goes looking:

- Missions and badge tiers beyond the achievement catalogue
- Recurring chores and automatic chore rotation
- A notification settings page beyond the per-category toggles
- Weekly / monthly leaderboard windows (the leaderboard is all-time)
- Reports and export
- An admin panel
- Receipt OCR and UPI payment links
- Chat, polls and shared shopping lists
- Multi-house membership and a house switcher
- Real-time updates over Socket.IO (the unread badge polls a count endpoint instead)

The `Notification` and `Activity` models and their writes are in place — only some of the browsing
surface is deferred.
